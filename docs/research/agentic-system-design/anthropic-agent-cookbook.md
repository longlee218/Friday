# Anthropic Agent Cookbook

Runnable code counterpart to Anthropic's "Building Effective Agents" post: notebooks implementing each named workflow pattern, plus newer material on multi-agent orchestration and the Claude Agent SDK's "dynamic workflows" feature. Currently lives at **`anthropics/claude-cookbooks`** (the old `anthropics/anthropic-cookbook` URL now redirects there — old links resolve, but the canonical org/repo is `claude-cookbooks`). The pattern examples are under `patterns/agents/`; a second, newer directory `claude_agent_sdk/` holds SDK-based agent examples including one on dynamic workflows.

## Patterns found, with code shape

**Prompt chaining, routing, parallelization** — [`patterns/agents/basic_workflows.ipynb`](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/basic_workflows.ipynb), built on [`patterns/agents/util.py`](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/util.py)'s two primitives: `llm_call(prompt, system_prompt, model)` (thin wrapper over `client.messages.create`) and `extract_xml(text, tag)` (regex tag extraction — no JSON mode, no schema validation). All three patterns are one-function implementations: `chain(input, prompts: list[str])` folds a list of prompts sequentially, feeding each step's output as the next step's input string. `parallel(prompt, inputs, n_workers=3)` fans the *same* prompt out over a `ThreadPoolExecutor` and collects results — no synthesis step, just a list back. `route(input, routes: dict[str,str])` does a single classification call asking the model to pick a key from `routes.keys()` inside `<reasoning>`/`<selection>` XML tags, then dispatches to that route's prompt — a hardcoded key set, not a dynamically discovered one.

**Orchestrator-workers** — [`patterns/agents/orchestrator_workers.ipynb`](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/orchestrator_workers.ipynb). A `FlexibleOrchestrator` class holds two prompt templates (orchestrator, worker) and runs `process(task, context)` in two phases: (1) one call to the orchestrator prompt returns `<analysis>` plus a `<tasks>` block of `<task><type>/<description></task>` entries, parsed by a hand-rolled line-scanning `parse_tasks()` (not a proper XML parser); (2) the code loops over the parsed tasks **sequentially** (the notebook's own "Limitations" section flags this and suggests `asyncio`/thread pools as an exercise), calling `llm_call` once per task with the original task plus that task's type/description, and validates each worker's `<response>` isn't empty before collecting it. No synthesis step is built in — the README's "Next Steps" explicitly names "add a synthesis phase" as unimplemented future work.

**Evaluator-optimizer** — [`patterns/agents/evaluator_optimizer.ipynb`](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/evaluator_optimizer.ipynb). `generate(prompt, task, context)` returns `(thoughts, result)` parsed from `<thoughts>`/`<response>` tags; `evaluate(prompt, content, task)` returns `(evaluation, feedback)` parsed from `<evaluation>`/`<feedback>` tags, where `evaluation` is expected to literally be the string `"PASS"` or something else. `loop()` calls `generate` once, then repeats `evaluate` → (if not `"PASS"`) rebuild a `context` string listing every previous attempt plus the latest feedback → `generate` again, forever until the evaluator says `PASS`. There is no turn cap in the loop as written — an explicit gap vs. Friday's `max_turns=1` correction-budget design.

**Async multi-agent orchestration** — [`patterns/agents/async_multi_agent_orchestration.ipynb`](https://github.com/anthropics/claude-cookbooks/blob/main/patterns/agents/async_multi_agent_orchestration.ipynb), framed as showing "the shape of the two multi-agent orchestration patterns behind the multi-agent results in the Claude Opus 4.8 system card." A `Hub` class holds per-agent inboxes and `asyncio.Event`s; two tools, `send_message`/`wait_for_message`, are the *only* channel between agents. One `run_agent()` drives any agent's tool-use loop and **appends the drained inbox onto the last tool result** each turn rather than polling. Part 1 runs a **fixed N-agent team** (`asyncio.gather` over pre-named peers). Part 2 gives a "lead" agent three more tools (`create_subagents`, `get_status`, `kill_subagents`) that dynamically `asyncio.create_task()` new helpers at runtime, poll status, and cancel them when done.

**Dynamic workflows (Claude Agent SDK)** — [`claude_agent_sdk/08_Dynamic_workflows.ipynb`](https://github.com/anthropics/claude-cookbooks/blob/main/claude_agent_sdk/08_Dynamic_workflows.ipynb), newer material, distinct from the `patterns/agents` set. Claude itself writes a JavaScript orchestration script and hands it to a `Workflow` tool, which a runtime executes in the background (up to 16 concurrent subagents), with primitives `agent(prompt, options)` (spawns one subagent with a **clean context** — sees only its prompt string), `parallel([...])` (fan-out with a join barrier), `pipeline(items, stage1, stage2, ...)` (per-item multi-stage pipelines running independently), and `phase(...)` for progress grouping — with **plain JavaScript between calls** for filtering/merging/loops at zero token cost. The worked example is a fact-check workflow with four phases: EXTRACT (one agent pulls claims) → VERIFY (one agent *per claim*, parallel, structured-output schema) → SKEPTIC (a second pass re-examining only "confirmed" verdicts, routed in code) → REPORT (one agent compiles a table). The notebook states its own decision table as "who holds the plan": a single agent (Claude, turn by turn, plan in context), subagents (Claude, turn by turn, plan in lead agent's context), or a dynamic workflow (a script decides, plan in script variables, resumable, scales to "dozens to hundreds of agents").

## Relevance to Friday

**Dynamic workflows vs. `friday/dag/engine.py`.** None of the cookbook's `patterns/agents` examples use a hand-rolled graph framework like Friday's checkpointed `dag/engine.py` — they lean entirely on either bare loops (`chain`, `loop`) or the SDK's own orchestration primitives. Dynamic workflows are the closest cookbook analogue to what Friday built by hand: a script (there, JS generated by Claude at runtime; in Friday, Python written by a person ahead of time) that decides node order deterministically, with model calls as opaque steps and control flow (filtering, branching, barriers) in plain code between them. The cookbook's own "who holds the plan" table is exactly Friday's `DESIGN.md` argument for keeping workflows as "deterministic Python, and an agent is a node inside one" — the cookbook arrived at the same conclusion (plan-in-code beats plan-in-context past a certain fan-out) from the runtime-feature side rather than the hand-rolled-framework side.

**Orchestrator-workers vs. the Diagnose/Collector design.** The fact-check workflow's four-phase shape — EXTRACT → VERIFY (parallel, one per item, clean context each) → SKEPTIC (code-routed re-check of only the "confirmed" subset) → REPORT — maps closely onto `.scratch/read-it-the-way-the-operator-does/`'s Gather (parallel, deterministic Source checks) → Diagnose (reasoning step) → bounded `collect` tool invoking a Collector sub-agent. The mapping: Friday's parallel Source checks ≈ the workflow's `parallel([...])` VERIFY fan-out (each check reads one thing fresh, no shared context); Friday's Diagnose reasoning step ≈ the workflow's code-level routing logic that decides what runs next (in the cookbook, plain JS; in Friday, the DAG's node code) rather than a model choosing edges; Friday's Collector sub-agent, invoked via one `collect` tool ≈ the workflow's `agent(prompt, options)` spawn — a single-purpose worker with a clean, narrow context. The `async_multi_agent_orchestration.ipynb`'s inbox-on-tool-result mechanism is a different, chattier shape (bidirectional messaging between long-lived peers) that doesn't fit Friday's bounded, one-shot Collector call as well as the workflow's fire-and-collect `agent()` primitive does.

**Evaluator-optimizer vs. Friday's eval-less extraction/investigation.** The cookbook's `loop()` is the one pattern with no built-in stopping bound — it retries until the evaluator emits `"PASS"`, with no `max_turns` equivalent, which is the opposite of Friday's stated `max_turns=1` "correction budget is one turn" design for its own agents. It is a plausible shape for a *future* Diagnose-quality gate (a generator producing a diagnosis, an evaluator checking it against evidence before handing over), but as published it is a loop Friday's own turn-budget philosophy would reject unmodified — any adoption would need a hard cap bolted on, which is exactly the gap board `every-answer-has-a-shape` ticket 03 leaves open (no evaluation rows yet) and ticket 07 defers (baseline before re-running the eval). Nothing in the cookbook addresses building the labeled evaluation set itself — that stays a Friday-side/operator problem.
