# Writing Effective Tools for Agents — Anthropic

Anthropic engineering post on designing, evaluating, and iterating on tools built for agents rather than for human developers or deterministic callers.

URL: https://www.anthropic.com/engineering/writing-tools-for-agents
Published: 2025-09-11. Lead author Ken Aizawa, with contributions from Barry Zhang, Zachary Witten, Daniel Jiang, and others on Anthropic's applied AI / agent teams.

## Key concepts

**Tools are a new kind of contract.** The post frames a tool definition as "a contract between deterministic systems and non-deterministic agents" — unlike a function signature between two programs, an agent given a `get_weather` tool "might call the weather tool, answer from general knowledge, or even ask a clarifying question about location first." The design goal it states directly is to "increase the surface area over which agents can be effective," not to expose the most functionality.

**Choose the right tools, don't just wrap the API.** The post is explicit that not every API endpoint should become a tool one-for-one. Its examples: prefer `search_contacts` over `list_contacts` (agents have limited context to page through), and consolidate `read_logs` / `list_users` / `create_event`-style multi-step workflows into fewer, higher-level tools rather than exposing every primitive. This is a direct statement of the "high-level over exhaustive" tradeoff.

**Namespacing for tool-selection clarity.** Prefixed, service-scoped names like `asana_projects_search` and `asana_users_search` are recommended specifically because they let an agent disambiguate between similarly-shaped tools from different systems, and because encoding structure in the name itself "offloads logic" that would otherwise have to live in the description or be inferred at call time.

**Response shaping: signal over completeness.** Tool responses should favor human-readable, high-signal fields over technical identifiers (UUIDs, raw internal IDs). The post's concrete mechanism is a `ResponseFormat` enum letting the *agent* request "concise" vs. "detailed" output — in their measurements this cut token consumption by roughly two-thirds for the concise path, without giving up the option to fetch full detail when actually needed.

**Token efficiency as a first-class design axis.** Pagination, filtering, range selection, and truncation-with-sensible-defaults are treated as required tool behaviors, not optional polish. Truncation specifically should come with "helpful instructions" steering the agent toward a token-efficient next call (e.g., how to narrow a query) rather than silently dropping data. Error messages should name the specific problem and a corrective action, not return an opaque code.

**Prompt-engineer the tool description like onboarding docs.** The post's own framing: "describe your tool to a new hire." Implicit domain knowledge — query syntax, vocabulary, how resources relate to each other — has to be made explicit in the description, because the model has no other channel to learn it. It cites a measured case: refining tool descriptions alone produced a documented performance gain for Claude Sonnet 3.5 on SWE-bench Verified.

**Evaluate with realistic, multi-tool tasks, and read what's missing.** Good eval tasks are grounded in genuine workflows (e.g., "schedule a meeting with document attachments," "correlate a customer issue across several data sources") and should require several tool calls to complete, not one. The post explicitly flags that what an agent's response *omits* is often more diagnostic than what it includes when debugging a bad trajectory.

**Close the loop with an agent, not just a human, doing the iteration.** The workflow described is: prototype a tool (often wrapped as a local MCP server via `claude mcp add`), run it against eval tasks, then hand the transcripts back to Claude Code to analyze failures and refactor the tool definition/description itself. The post reports this iterative, agent-assisted refinement outperforming hand-tuned internal Slack and Asana tools built by humans alone.

## Relevance to Friday

**Namespacing.** Friday's structure — every tool in `friday/kernel/tools/`, one module per subject (`memory.py`, skills-related tools, etc.) — matches the *organizational* half of the source's namespacing advice (grouping by subject/service), but Friday's actual tool names are not shown to be prefixed the way the source's `asana_projects_search` / `github_list_prs` examples are. The source's namespacing argument is about what the **model sees in the name string**, not just where the code lives; if Friday's tool names don't already carry a subject prefix, that's a gap worth checking against `tests/test_tools.py`'s asserted list — cheap to fix if so, since the test already pins the exact name set.

**Docstring-driven descriptions as single source of truth.** Generating triage's `Decided` enum description per task type from each `Params` dataclass's own docstring — and refusing import when a class has no real docstring — is a stronger version of the source's "provide extremely detailed descriptions" advice: it makes the description *impossible to drift* from the type it describes, because there is only one place to edit it. The source's own case study (SWE-bench gains from description refinement alone) is evidence for why Friday is right to treat this as worth enforcing at import time rather than leaving as a convention.

**Four skill tools split by agent knowledge vs. Anthropic's consolidation advice.** The source's explicit example (`list_contacts` → `search_contacts`, three CRUD verbs → one tool with an `action` param) argues for *consolidating* overlapping operations into fewer tools to reduce selection ambiguity. Friday's `fetch_skill` / `search_skills` / `describe_skill` / `read_skill_file` is four tools rather than one — but the split isn't along the axis the source warns about (near-duplicate verbs on the same resource); it's along **what the calling agent already knows** (a name vs. no name) and **how much it should pay** (metadata vs. full body), which is closer to the source's own `ResponseFormat` concise/detailed pattern than to the anti-pattern it warns against. The source's "reduce selection ambiguity" concern would apply if `fetch_skill` and `search_skills` were interchangeable ways to do the same lookup; they aren't — one requires an input the other doesn't produce. This design is defensible under the source's own logic, but it's the one place in Friday's tool inventory where a reviewer applying the source superficially ("four tools, should be one") would push back incorrectly without reading the actual call-time distinction.

**`failure_error_function` as response-shaping, not just error handling.** The source's "error messages should be specific and actionable rather than generic error codes" is aimed at *content* — Friday's `harness.tool` wrapper is solving an adjacent but distinct problem: *which channel* a failure travels on. Returning a string ("unavailable, try again") instead of letting the SDK format a raw exception back to the model is exactly the kind of response-shaping the source cares about (bounding what reaches the agent's context, avoiding a leak of internal detail like a path or credential) — but Friday's stated reason (avoiding a blind retry that double-writes) is an operational safety concern the source doesn't discuss; the source's failure-message guidance is about clarity for the *next* tool call, not about idempotency of a retried write. The two concerns point the same direction here, but they're not the same argument, and Friday's is the stricter one.

**Consolidated one-node graphs vs. tool consolidation.** The source's consolidation advice is about *tool* surface, not workflow *graph* shape, but the underlying principle — fewer, higher-level units beat many low-level ones when the low-level ones are always used together — is the same argument `docs/DESIGN.md` makes for collapsing every task type onto one `dag` node (extract → validate → ask-or-hand-over) instead of a bespoke multi-step graph per type. Worth naming explicitly if this document is later used to justify that decision to someone unfamiliar with the DAG ticket history.
