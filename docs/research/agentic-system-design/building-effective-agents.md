# Building Effective Agents — Anthropic

Anthropic's practitioner-oriented writeup on agentic system design, published simultaneously as a Research piece and an Engineering post: [anthropic.com/news/building-effective-agents](https://www.anthropic.com/news/building-effective-agents) / [anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents). Published 2024-12-19, by Erik Schluntz and Barry Zhang.

## Key concepts

**The augmented LLM.** The base unit of every pattern below: "the basic building block of agentic systems is an LLM enhanced with augmentations such as retrieval, tools, and memory" (https://www.anthropic.com/engineering/building-effective-agents). Everything else in the post is a way of composing this one unit.

**Workflows vs. agents — a named, load-bearing distinction, not a synonym pair.** Workflows are "systems where LLMs and tools are orchestrated through predefined code paths"; agents are "systems where LLMs dynamically direct their own processes and tool usage, maintaining control" over how a task gets done (https://www.anthropic.com/engineering/building-effective-agents). The difference is who decides the next step — code, or the model.

**Prompt chaining.** Decomposes a task into a fixed sequence of LLM calls, "each LLM call processes the output of the previous one," typically with programmatic checks between steps. Best "when a task can be easily and cleanly decomposed into fixed subtasks," trading latency for higher accuracy on each step (https://www.anthropic.com/engineering/building-effective-agents).

**Routing.** "Classifies an input and directs it to a specialized followup task" — one model call (or a lighter classifier) picks a path, and each path can have its own specialized prompt. Fits problems with distinct, separately-optimizable categories, where a single generalized prompt would trade off accuracy on each category (https://www.anthropic.com/engineering/building-effective-agents).

**Parallelization**, in two variants: *sectioning* — splitting a task into independent subtasks run concurrently, and *voting* — running the same task multiple times to get diverse outputs and aggregating (e.g., majority vote, or a check that requires multiple independent passes to agree). Both trade extra calls for speed (sectioning) or confidence (voting) (https://www.anthropic.com/engineering/building-effective-agents).

**Orchestrator-workers.** "A central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results." Unlike parallelization, the subtasks aren't fixed in advance — the orchestrator decides them at runtime based on the specific input, which suits "complex tasks where you can't predict the subtasks needed" (https://www.anthropic.com/engineering/building-effective-agents).

**Evaluator-optimizer.** "One LLM call generates a response while another provides evaluation and feedback in a loop," repeating until the evaluator is satisfied. Effective "when we have clear evaluation criteria, and when iterative refinement provides measurable value" (https://www.anthropic.com/engineering/building-effective-agents).

**Autonomous agents**, as opposed to any of the above workflows: the model plans and acts in a loop, using tool results as ground truth to decide its own next step, until it determines the task is done or hits a stopping condition. The post is explicit that this shape is warranted only for "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path," and it comes with "higher costs, and the potential for compounding errors," which is why it calls for "extensive testing in sandboxed environments, along with appropriate guardrails" (https://www.anthropic.com/engineering/building-effective-agents).

**The core restraint principle**, stated repeatedly rather than once: "find the simplest solution possible, and only increasing complexity when needed"; "for many applications, optimizing single LLM calls with retrieval and in-context examples is usually enough"; and, as the closing framing, "success in the LLM space isn't about building the most sophisticated system. It's about building the right system for your needs. Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short" (https://www.anthropic.com/engineering/building-effective-agents).

## Related primary sources found

- **[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)** (Anthropic Engineering, 2025-06-13). A production case study of the orchestrator-workers pattern named above, at scale: "a multi-agent architecture with an orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." It reports a 90.2% improvement over single-agent Claude Opus 4 on Anthropic's internal research eval, and — most relevant to a "should we add this pattern" question — an explicit cost gate: multi-agent is worth it only for "tasks where the value of the task is high enough to pay for the increased performance," specifically "valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools," while noting coding tasks (few parallelizable components) and tasks needing shared context across all agents are poor fits for the pattern today.
- **[anthropics/claude-cookbooks](https://github.com/anthropics/claude-cookbooks), `patterns/agents/`** — runnable notebooks implementing the same taxonomy: prompt chaining, routing, parallelization, `orchestrator_workers.ipynb`, `evaluator_optimizer.ipynb`, and a newer `async_multi_agent_orchestration.ipynb`. The directory's own README attributes the patterns directly to the Building Effective Agents paper by Schluntz and Zhang, confirming the two documents describe one taxonomy rather than two.

## Relevance to Friday

**Friday's single-node-per-type design is a workflow, not an agent, and that's a correct and deliberate choice by this taxonomy — not a stage the design is stuck at.** CLAUDE.md is explicit that "the graph's *shape* is code — a model never chosen the next step," and every task type currently collapses to one node (extract → validate → ask-for-missing/hand-over). By Anthropic's definition, "workflow" is precisely "predefined code paths," and Friday's `friday/dag/router.py` choosing the graph by task type, not by model judgment, is exactly that. The prior 5-node `api_issue` graph was removed for being an *undesigned* workflow, not for being the wrong shape of thing — nothing in the post argues a single-node workflow is under-engineered; it argues the opposite, that a workflow should stay as small as the task actually requires.

**The `.scratch/read-it-the-way-the-operator-does/` Diagnose/Collector redesign is choosing between routing+orchestrator-workers (a workflow) and a true agent, and the post's own criteria answer which one fits.** An investigation task — gather diagnostic facts, decide what's missing, ask or escalate — is bounded (the operator can enumerate the diagnostic dimensions in advance) rather than open-ended, and Friday's own architecture constraints already forbid the shape that would make it a true "agent": "a model never chooses the next step," and there is no `apply_fix`-style tool for it to act through unsupervised. That points toward an **orchestrator-workers** shape (a Diagnose orchestrator that dynamically decides which Gather checks are relevant to the report at hand, dispatching to fixed worker functions) rather than a full autonomous loop — and the post is explicit that orchestrator-workers is the pattern for exactly this shape of problem: "complex tasks where you can't predict the subtasks needed," as opposed to parallelization's fixed, pre-enumerated subtasks.

**The deterministic "Gather" checks plus the model-driven "Collector" tool is closer to routing-into-a-worker than to orchestrator-workers as Anthropic defines it**, and the distinction matters for where the model gets to decide. If a fixed set of Gather checks always runs and the Collector only interprets their output, that's a fixed pipeline (prompt chaining/parallelization) with one LLM step, not orchestrator-workers — the orchestrator pattern specifically means the *decomposition itself* is chosen by a model call at runtime. Friday's board should decide explicitly which of these it wants, since CLAUDE.md's own architecture rules (no model chooses the next graph step) would forbid the Collector from picking which Gather checks to run, only from interpreting their already-fixed output.

**Nowhere in Friday is there an evaluator-optimizer loop, and one candidate exists: the responder's `friday/responder/check.py` floor.** That module currently applies a fixed set of static rules (no link, no code block, length, no promise) to reject a draft outright and fall back to a template — a one-shot gate, not a loop. Evaluator-optimizer would instead feed the rule violations back to the responder for a second, corrected draft before falling back — plausible given the "one correction budget" pattern Friday already uses elsewhere (`max_turns` for tool-call answers), but it would be a second model call on the highest-volume unattended send path in the system, and the post's own gate — "clear evaluation criteria, and iterative refinement provides measurable value" — is arguably already satisfied by the deterministic check without paying for a second LLM call. This is worth flagging as a considered no, not an oversight, if the board revisits it.

**The multi-agent research system's cost gate is the sharper test for Friday than the base post's, and it argues against multi-agent here.** Friday's tasks are not "heavy parallelization, information that exceeds single context windows" work — they're single-report, single-reporter triage tasks bounded by one Discord conversation, which is closer to the coding-task counterexample the multi-agent post itself gives ("fewer parallelizable components") than to its research-query sweet spot. This reinforces the workflow (not multi-agent) framing above from the cost side, independent of the control-flow argument.
