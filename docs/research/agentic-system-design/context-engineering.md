# Effective Context Engineering for AI Agents — Anthropic

Anthropic's engineering-blog treatment of context management for agents: why context is a finite, decaying resource, how to calibrate system prompts and tools, and four techniques (compaction, structured note-taking, sub-agent architectures, just-in-time retrieval) for keeping long-running agents coherent.

URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Key concepts

**Context engineering vs. prompt engineering.** Prompt engineering is "writing and organizing LLM instructions for optimal outcomes" for a discrete task. Context engineering is the broader, iterative discipline: as an agent loops and accumulates ever more data (tool results, retrieved documents, its own prior turns), context engineering decides which subset of that growing universe of tokens actually enters the limited window on each inference step.

**Context rot.** Built on needle-in-a-haystack-style research: as token count in the context window grows, a model's ability to accurately recall and reason over that context degrades. The stated mechanism is architectural — transformer attention creates n² pairwise token relationships, so those relationships "get stretched thin" as length grows, and models are trained mostly on shorter sequences, leaving "fewer specialized parameters for context-wide dependencies." The effect is not a cliff but a gradient: reduced precision on retrieval and long-range reasoning, not a hard failure point. Anthropic frames this with a human analogy — an "attention budget" akin to working memory, spent down as more tokens are added — which is why context is described as a finite resource with diminishing marginal returns rather than a container to fill.

**System-prompt calibration ("the right altitude").** Two named failure modes: prompts that hardcode "complex, brittle logic" to force exact behavior (fragile, expensive to maintain), and prompts so vague they "falsely assume shared context" and give the model no concrete signal. The target is "specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics." Practical guidance: organize with XML tags or Markdown headers (e.g. `<background_information>`, `<instructions>`, `## Tool guidance`) and aim for the *minimal* set of information that fully specifies expected behavior — minimal is not a synonym for short.

**Tool design's effect on context.** Tools are the contract between an agent and its action/information space, so a bloated or ambiguous tool set burns context on indecision, not just on tokens. Anthropic's test: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." Tools should be self-contained, robust to error, unambiguous in intended use, and minimize functional overlap. Few-shot examples should be a small set of diverse canonical cases rather than an exhaustive enumeration of edge cases — "pictures worth a thousand words" for the model, not a decision tree.

**Four techniques for long-horizon context management:**

1. **Compaction** — summarize a conversation nearing its context limit and reinitiate with the summary, preserving "architectural decisions, unresolved bugs, and implementation details" while discarding redundant tool output. The tuning axis is recall-then-precision: start by over-capturing so nothing load-bearing is lost, then trim. A cheap first cut named explicitly: clear tool-call results once they've served their purpose. Claude Code is cited as an implementation that additionally keeps recently-accessed files alongside the compressed summary.
2. **Structured note-taking (agentic memory)** — the agent periodically writes notes to storage outside the context window and reads them back later, giving persistent memory "with minimal overhead" across resets. The cited example is Claude playing Pokémon, tracking exact step counts and strategy across thousands of steps by consulting its own notes rather than holding it all in-window. Anthropic ships this as a public-beta memory tool on the Claude Developer Platform (`/memories` file directory, client-executed `view`/`create`/`str_replace`/`insert`/`delete`/`rename` commands — verified directly from platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).
3. **Sub-agent / multi-agent architectures** — instead of one agent carrying all state for an entire task, specialized sub-agents do deep work in their own clean context windows and return only a condensed summary (cited figure: 1,000–2,000 tokens) to a lead agent that plans and synthesizes. This isolates "detailed search context" inside the sub-agent so the lead's window stays focused on synthesis. Anthropic points to its own "How we built our multi-agent research system" post, which reports substantial gains over single-agent baselines on complex research tasks (independently verified via search: ~90% improvement over single-agent Opus on Anthropic's internal research eval, at roughly 15x the token cost of a single chat turn — anthropic.com/engineering/multi-agent-research-system).
4. **Just-in-time retrieval vs. pre-loading** — rather than embedding-based retrieval that stuffs relevant documents into context before inference, agents keep lightweight identifiers (file paths, stored queries, links) and load data at runtime via tools. Claude Code's example: writing targeted DB queries and using `head`/`tail` over large outputs instead of loading full data objects. Framed as mirroring human cognition — external indexes (file systems, bookmarks) instead of memorizing corpora — and as enabling progressive disclosure, where structural metadata (a file named `test_utils.py` under `tests/` vs. under `src/core_logic/`) carries signal for free. Named trade-off: runtime exploration is slower and requires "opinionated and thoughtful engineering" to stop an agent wasting context on dead ends. Recommended default is hybrid: pre-load what's cheap and stable (Claude Code's `CLAUDE.md`), explore just-in-time for everything else (glob/grep instead of a stale pre-built index).

The umbrella principle stated for all four: find "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome."

## Relevance to Friday

**Compaction: Friday's version is a stricter, cost-motivated subset, not the same technique.** Anthropic's compaction is model-assisted summarization — an LLM call condenses history, trading recall for precision. `friday/extraction/context.py`'s `build_full_context` compaction (CLAUDE.md's ticket 08/D5–D7) is truncation only: it drops the *oldest whole messages* once over budget, never summarizes, and CLAUDE.md records this as a deliberate scope boundary — a model call on every over-budget task would cost real money on the highest-volume paths and would break the provider's prompt-cache prefix by rewriting it every pass. Judged against Anthropic's own guidance, this is defensible rather than a cruder cousin with nothing behind it: Anthropic's "low-hanging" cheap compaction move — clear stale tool-call results before reaching for summarization — is exactly Friday's chosen ceiling, and Anthropic's own compaction section warns that "overly aggressive compaction can result in loss of subtle but critical context whose importance only becomes apparent later," which is precisely the failure mode whole-message truncation is designed to avoid (a kept message is never partially rewritten by a model that might drop the wrong clause). What's missing relative to Anthropic's fuller technique: no path at all for a single message that itself exceeds budget — Friday's two-strikes "compaction cooldown" surfaces that as a visible, operator-facing failure (`/api/tasks/{id}/compaction`) rather than solving it, which is consistent with the project's stated preference for a legible failure over a silent, possibly-wrong model-authored summary.

**LightContext/FullContext maps onto the pre-load vs. just-in-time split, but both of Friday's contexts are still pre-loaded, not explored.** Anthropic's "just-in-time" pattern is specifically about an agent holding *lightweight identifiers* and dynamically fetching via tools at its own discretion (Claude Code's glob/grep). Friday's triage path (`friday/triage/context.py`'s `build_light_context`, ticket 09/14) is closer to Anthropic's *pre-loading* side done well: it deliberately bounds what's assembled (structured room summary + current turn only, no unbounded transcript) and the gain is measured, not assumed — three tests proving >90% shared prompt-prefix bytes between calls. That is Anthropic's stability argument for pre-loading, empirically validated, but it is still whole-context assembly by a deterministic function before the model runs — the model never chooses to fetch more. `FullContext` for extraction is the same shape at a larger budget. Neither is just-in-time retrieval in Anthropic's sense, because no Friday agent holds a tool that lets it decide *at runtime* to pull more transcript, more memory, or a specific artifact — everything is decided by `prepare_node`/`build_full_context` ahead of the call. That is consistent with Friday's other constraint (bounded turn budgets: one call plus one retry) — true agent-directed exploration assumes turns to spend exploring, which a one-shot extractor doesn't have — but it means Friday is currently on the "opinionated pre-computed" side of Anthropic's stated hybrid, not actually hybrid.

**The memory-injection-vs-tool-call split matches Anthropic's sub-agent/context-isolation logic more than its memory-tool pattern, and Friday's own reasoning for it is explicit and matches Anthropic's.** Anthropic's memory tool is tool-call based for every caller — the isolation argument in the source is about *sub-agents* returning condensed summaries, not about splitting which agents get read/write tool access to memory. Friday's actual split (CLAUDE.md, ticket 09/12) is narrower and better justified by a different constraint from the same source: extraction gets memory via prompt-section injection because "its turn budget is one call plus one retry and a tool-result round trip would spend it on searching" — i.e., Friday independently arrived at the same trade Anthropic names for sub-agents (a tight budget forces information to arrive pre-assembled rather than fetched), just applied to tool-call-vs-injection instead of sub-agent-vs-lead-agent. The responder, which is not turn-constrained the same way, gets full read/write tool access (`memory_search`/`memory_add`/`memory_propose`/etc.), matching Anthropic's model of memory as an agent-directed retrieval surface for an agent with room to explore. Anthropic's other rule — memories reach a model only as a tool result or an assembled section, never appended into `instructions` — is also independently present in Friday and for a related reason (a tool result can't retroactively rewrite the cached prompt prefix the way an appended instruction could), and Friday adds a guarantee the source doesn't mention: `html.escape` at the write seam so a stored memory value can't forge a second prompt-section boundary. That's a Friday-specific hardening beyond anything in the primary source, worth keeping in mind as a place Friday's design is ahead of, not behind, the reference material.

**One live tension worth flagging:** Anthropic's compaction and sub-agent techniques are explicitly for arbitrarily long-running, open-ended agent loops (Claude Code sessions, deep research). Friday's tasks are architecturally one-node graphs with a one-retry turn budget by design — the entire "long-horizon" problem space the source's compaction/sub-agent sections address mostly doesn't arise for Friday's current task types. That's why Friday's compaction only needs to be a budget-fitting truncator rather than a full summarizer: the source's heavier techniques are answers to a problem (multi-hour, many-turn agent loops) Friday has deliberately not built yet. If Friday ever grows a genuinely multi-node, long-running graph (the retired five-node `api_issue` graph hints this was tried once), Anthropic's compaction-with-model-summarization and sub-agent-with-condensed-return patterns become directly applicable in a way they currently are not.
