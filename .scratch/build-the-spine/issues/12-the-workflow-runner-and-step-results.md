# The WorkflowRunner and `step_results`

Decisions: [The runner and adaptive replan](../../domains-plug-in/issues/13-the-runner-and-adaptive-replan.md)
(as amended by 16, 17), [The target module layout](../../domains-plug-in/issues/09-the-target-module-layout.md) §7–8.

## Goal

`friday/kernel/spine/runner.py`, plain code, not wired to the pool yet.

- `StepResult` ORM row, table `step_results`, key `(task_id, step_key)`
  (Alembic, autogenerated against a throwaway db); `store/repositories/plans.py`.
- Walk the frozen plan: stored final result → skip, hand to readers; else
  run the step; step failure → `STEP_ATTEMPTS` (2) → `HandOver step_failed`.
- Agent `Ask`/`HandOver` → store, stop. `Replan` → store; replans used =
  `max_replans` → `HandOver replans_exhausted` (every version, every result,
  last `found`); else Planner → GatePlan → run v(n+1) from its first step.
  A reused `Replan` is data, never a new signal.
- `Retriage` → store, stop (the retriage step itself is 17).
- `draft` step: core responder over `reads` + intake context (the responder
  switch itself is 14).

## Acceptance

- [ ] Replan reuse cases from ticket 13 §6 (change direction / build on /
      stop) each tested; no loop possible.
- [ ] `replans_exhausted`, `step_failed` tested.
- [ ] Guard: only the runner writes `step_results`.
- [ ] Whole suite green; `code-review` done.
