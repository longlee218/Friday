# 09: Twelve kinds, one table, and a place to type them

**What to build:** `origin`, `key` and `data` on `memories`; the seven new
kinds with a schema each; `readers_for`; an admin write route and the UI
form behind it.

**Blocked by:** nothing.

**Decisions:** spec, "Memory: one store, twelve kinds".

**Status:** ready-for-agent

## What

- Alembic migration adding the three columns and the partial unique index,
  autogenerated against a throwaway database (`CLAUDE.md`, Environment).
  Existing rows: `origin='model'`, `key` and `data` null.
- `MemoryKind` grows to twelve. A second, smaller enum is what the memory
  tools expose to a model — five values, unchanged — and a test asserts the
  tool schema offers nothing else.
- One dataclass per structured kind; `data` is validated with the same
  `fits` the harness uses, at `Database.memory_add` — the one door, where
  the instruction-shape guard already stands. The guard runs over `text`
  only.
- A model-origin call may not update, supersede or delete an admin row;
  it gets the same "no such memory" a wrong-scope id gets.
- `readers_for(kind) -> frozenset[str]`; `DOMAIN_KINDS` stays derived from
  it. `db.domain_memories` is unchanged for the extractor; a new reader
  serves `Diagnose` (kinds 1–4 and matching 6).
- `POST/PUT/DELETE /api/channels/{id}/memories` for `origin=admin`, each
  returning the guard's reason on refusal. The Rooms or Context screen gets
  a form per kind: a text area for prose kinds, fields for structured ones.
  `web/src/api-types.ts` and `tests/test_web_contract.py` move together.

## Verify

- Whole suite; `tests/test_migrations.py` green.
- Each schema: a wrong-typed `data` is refused with the field named.
- Delete the admin-row protection once and watch its test go red.
