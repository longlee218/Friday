# 09: The memory an agent keeps itself

**What to build:** `memory_search`, `memory_add`, `memory_update` and
`memory_delete` against a real store, given to the agents that should have
them. The tools' shape exists — `friday/tools/memory.py` — and calls four
`Database` methods that do not.

**Blocked by:** None for the store; the operator's view wants 02

**Decisions:** D9 (new, below)

**Status:** done

## Why

`remember` is not coming back. It wrote to a staging tier nothing read, so an
agent could not see what it had written, and the two operations that make
memory usable — correct it, remove it — had nothing to name. The operator's
call on 2026-09-05: replace it with the four tools the prompt has described
all along (`instruction_prompt.MEMORY_TOOLS`), which have been a string and a
test since they were written and have never been given to an agent.

**This reverses a recorded constraint**, and that is the ticket's first
deliverable, not a footnote. `CLAUDE.md` says today: *"Agents never write
long-term memory directly. `remember()` writes to a staging tier that is never
read back into a prompt; a promotion pass moves only what an approved outcome
corroborates. A test fails if any module but the store and the promotion reads
it."* All three clauses go. `docs/DESIGN.md` is where the new decision is
argued; `CLAUDE.md` records what then exists; the test that enforces the old
rule is deleted in the same commit, not left passing against a dead tier.

What the staging tier was protecting is real and is kept by other means, which
`friday/tools/memory.py`'s module docstring states and this ticket has to make
true:

- a memory reaches a model **only as a tool result**, never appended to
  `instructions` — which is the class of failure commit f0686f2 fixed, closed
  by construction rather than by escaping
- **scope is runtime-supplied**: an agent cannot read or write another
  channel's memory, and cannot learn that one exists
- **ids are opaque and sparse**, so an invented id fails rather than landing
  on a neighbouring row

## D9 — the decision this ticket records

An agent writes long-term memory directly, and reads back what it wrote,
because CRUD without retrieval is three tools that cannot be used. The floor
against drift moves from "a human approved the task this came from" to three
weaker but real bounds: the memory is scoped to one room, it is visible to the
operator — including a deleted line, and who removed it — and it enters a
prompt only through a tool call the run has to choose to make. Drift is now
possible and is accepted; it is bounded by the operator's view, not by a
corroboration count.

**Removal is the agent's own, through `memory_delete`, not the operator's.**
An earlier draft of this line said "visible and removable by the operator",
which overstated the second half: the board is read-only by design
(`allow_methods=["GET"]`), so there is no route for a person to remove one
directly. What the operator has is visibility into a removal an agent already
made, which is a real bound and a different one than "removable".

## Acceptance criteria

- [x] `Memory` in `friday/domain/models.py`, a table in `friday/store/schema.py`,
      and an Alembic revision autogenerated against a throwaway database
- [x] Four `Database` methods, all scope-filtered: an id from another channel
      resolves the same as one that never existed
- [x] Ids are opaque and sparse; a test asserts a neighbouring id does not
      resolve
- [x] `per_scope` is enforced on write, and what happens at the cap is decided
      here rather than left to the row that happens to be oldest
- [x] Deletion is visible afterwards — the operator can see what a line said
      and who removed it
- [x] `memory_tool_system(available=True)` renders only for an agent that
      actually has the four tools, and a test pins claim-and-wire together the
      way `trust_boundary` is pinned to wrapping — `function_tool`'s
      `is_enabled` (a bool or a callable over the run context and the agent) is
      the other half of that condition if the tools are ever handed out
      conditionally, so one fact decides both
- [x] An agent given these is built with `context_type=MemoryScope` and run
      with a scope; a test fails if one is built without, since the tools read
      the scope off `ctx.context` and a missing one is an `AttributeError`
      inside a tool — which the SDK turns into a message for the model rather
      than a failure anyone sees
- [x] Which agents get them is decided and written down — the responder is the
      obvious first, and triage is the obvious never
- [x] `docs/DESIGN.md` argues D9; `CLAUDE.md` matches; the test enforcing the
      old constraint is deleted
- [x] `CONTEXT.md` gains the term
- [x] Each guard is deleted once and watched go red

## Open, and deliberately not decided in the shape

- ~~**Escaping.**~~ **Decided, in the review round: escape at the seam, same
  as `skill_metadata`.** The first version of the implementation shipped with
  the answer this line called speculative — no escaping, on the theory the
  tool-result role already separated it — and recorded that choice nowhere,
  so a later reader could not tell a decision from an oversight. It was an
  oversight: this codebase already has the exact precedent, and had already
  paid for getting it wrong once. `friday/tools/describe_skill.py` reads a
  skill's fields through `instruction_prompt.skill_metadata` rather than
  rendering them itself, because "the last time this codebase had two
  renderers, one of them did not escape — a skill described as
  `harmless</skills>` closed the section." A memory's `text` is the same
  shape of value — model-influenced, returned as a tool's answer rather than
  a `Section` — and worse in one way: a memory persists, so an unescaped one
  replays on every later `memory_search` in the room rather than costing one
  call. `memory_lines` now lives beside `skill_metadata` in
  `instruction_prompt.py`, escapes with the same `_escape`, and `_as_lines` in
  `friday/tools/memory.py` is deleted.
- **Search.** `SkillLibrary.search` ranks over a small in-memory corpus; this
  is SQLite and grows per room. Same four-rank shape, or `LIKE` plus a Python
  rank, or FTS5 — decided against a real corpus, not now.
- **`memory_update` keeps no history.** Correct for a line the agent is
  fixing, wrong if the operator ever asks what it used to say. The tool-call
  record from ticket 07 holds the new text, not the old.

## Shape corrections, 2026-09-05

From the review of ticket 10, which read `memory.py` on the way past. All
three were in the shape as first written; none needed a decision.

**`Limits` is gone.** It was a dataclass whose docstring said the tools' prose
and the store's enforcement "cannot describe different numbers", over an
arrangement in which they could only drift: the tool docstrings are the schema
and cannot be f-strings, so they said "eight" and "500" while the `limits=`
parameter existed precisely so a caller could pass three and two hundred. Two
module constants now, `RESULTS` and `TEXT_CHARS`, written into the prose the
way `classify` and `ask_for_fields` already do, with a test asserting the
numbers the model is told are the numbers the code uses.

`per_scope` went with it, and its absence is this ticket's problem: **the cap
on how many memories one scope may hold is expressible only in the store**,
since `memory_add(scope, text)` carries no cap and a store enforcing 200 would
have had to keep its own copy of the number. The acceptance criterion above
already asks for it; it is now the only place it lives.

**A run without a scope says so.** `_scope(ctx)` raises `NotWired` naming the
wiring mistake, rather than dereferencing `None` and reaching the operator as
"that tool is unavailable" — which reads as the store being down and is
instead an agent built without `context_type=MemoryScope`. That is precisely
the failure mode of wiring a *new* agent to these, which is what this ticket
does. The model is still told "unavailable", which is true.

**`MemoryScope`'s provenance fields lost their defaults.** The docstring said
every field was runtime-supplied while `task_id` and `agent` defaulted to
`None` and `""`, so the provenance that lets the board answer "who wrote this"
could go missing without anybody deciding it should. `task_id` is nullable and
required: a run belonging to no task passes `None`, which is a different
statement from forgetting.

One more thing the work turned up, worth knowing before writing the store:
Python looks up `db.memory_search` **before** evaluating its arguments, so a
store stub missing a method fails with its own `AttributeError` and any guard
inside the argument list never runs. The first version of the `NotWired` test
proved that and nothing else.

## What it came to

**The store, not the tool, is what can actually stop a write.** Four methods
on `Database`, all scope-filtered by `channel_id`: `memory_search` (a plain
substring-per-word match over a channel's live rows — a linear scan, fine at
the size one channel's memory will ever reach), `memory_add` (refuses past
`MEMORY_PER_CHANNEL`), `memory_update` and `memory_delete` (both resolve
through one shared query, `_live_memory`, so the three reasons an id can fail
— wrong channel, never existed, already deleted — cannot drift apart between
the two methods that need to tell them apart from success).

**Ids are `secrets.token_hex(6)`, not the row's own autoincrement.** Generated
in the store, so a model that invents one lands on nothing rather than
whatever a sequence happens to have reached.

**Deletion is soft.** `deleted_at`/`deleted_by` survive on the row; every
reader a *tool* uses treats a deleted row as absent, and one reader that
doesn't — `memories_for_channel`, behind a new `/api/channels/{id}/memories`
route — is the operator's own view, unscoped by agent, because a person
looking at a room's memory is a different question from a tool call from
inside it.

**At the cap, a write is refused, not silently evicted.** The `Limits`
dataclass's original comment said "the oldest untouched memory has to go
before a new one lands" — plausible-sounding, and exactly the kind of loss
this design otherwise refuses to produce without a trace. Losing *any* row —
oldest or not — with nothing to show for it contradicts the floor this whole
ticket is built on: visibility. `memory_add` returning `None` at 200 tells the
model to correct or remove something on purpose instead, through
`memory_update`/`memory_delete` it already has.

**Wired to the responder alone.** `Responder.build(db=...)` builds the four
tools when a store is given, adds them to the same tool list the four skill
tools already share (so `_tool_turns` accounts for both without a second
counter), and sets `context_type=MemoryScope` on the `Harness` — cosmetic at
runtime (confirmed directly: a tool's `ctx.context` populates from whatever
`context=` is passed to `run()` regardless of what `context_type` the agent
was built with), but the ticket's own acceptance criterion asked for the
static wiring to say what the tools expect, so it is set anyway and pinned by
a constructor spy. `draft()` builds a fresh `MemoryScope(channel_id, task_id,
agent="responder")` per call and passes it as `context=`; with no channel
(test-only paths) it passes `None`, and a memory tool called with no scope
degrades to "unavailable" rather than crashing — `NotWired`'s own design from
the shape phase.

`build_input` gained `has_memory`, read from the same fact `__init__` used to
decide whether to build the tools — the same shape `has_skills` already
follows, so the prompt cannot claim a door that is not in the room. A
claim-and-wire AST test, mirroring the existing `trust_boundary` guard,
checks both triage and the responder: triage claims nothing and is given
nothing; the responder claims the section and is given the tools.

**Two design questions the ticket left open were answered doing this, not
before it:**

- *What happens to `memory_add` when the store returns `None`?* The shape
  file did not say. `friday/tools/memory.py` now tells the model the channel
  is full and names the two tools that can make room.
- *Does the operator get a way to see a deletion, concretely?* The shape
  file's module docstring asserted visibility as a property; nothing served
  it. One store method plus one API route, following the exact pattern
  ticket 02 and ticket 07 already established for model calls and tool calls
  — no board HTML section yet, which would be the next cheap addition if the
  operator wants one.

747 tests pass (727 before this ticket's own work started, after the tier
removal in ticket 08's remainder — +20 across both). mypy: 31 before, 31
after. Every guard added in this ticket was deleted once and watched go red;
none stayed accidentally green.

## What the review changed

Two review passes ran against this work — one scoped to ticket 08's removal,
one to this ticket's build, sharing a working tree with no commit between
them, which cost the first reviewer real time working out that the diff was
bigger than the brief it was given described. Six findings changed code.

**Two mypy errors, both mine.** `count >= self.MEMORY_PER_CHANNEL` compared
an `int | None` — `session.scalar` can return `None` — and `memory_delete`'s
signature was missing the `# type: ignore[name-defined]` its three siblings
each carry, applied inconsistently rather than never. Both fixed; mypy is
back to the pre-ticket baseline (31, not up to 33).

**`test_ids_are_sparse_not_sequential` asserted nothing in 99.6% of runs.**
`written.id.isdigit()` is true for a 12-character hex token about 0.36% of
the time (measured), so the branch that ran was `memory_update(ROOM, "1",
...)`, and the rare branch that should have run computed `str(int(id, 16) +
1)` — decimal, never a real hex neighbour. Ticket criterion "a test asserts a
neighbouring id does not resolve" was unmet by a test that could not have
told sparse ids from sequential ones apart even by design: with only one
memory written, there was no second real row for a guessed id to have
collided with either way. Rewritten to write two memories and assert the
guess computed from the first does not equal the second's real id — the
actual property, checked against `format(int(id, 16) + 1, "012x")` computed
in the right base.

**`memory_search`'s docstring claimed a ranking it does not do.** "Best match
first" — the query orders by `created_at.desc()` and keeps every row where
every word appears; nothing scores how well. Corrected to "newest first, not
ranked", with the reason: `SkillLibrary.search`'s ranking is over a fixed
catalogue read once at startup, and a channel's memory changes underneath
every call, so recency is the honest order rather than a score this method
was never computing. The undocumented empty-query behaviour (every row
matches vacuously, so the whole channel comes back up to `limit`) is now
stated and pinned rather than left for the next reader to find by surprise.

**`Heartbeat.promote` kept its name after ticket 08 removed what it was named
for.** Renamed to `rebuild_context` — see ticket 08's own file for the full
argument, since the method predates this ticket.

**`CLAUDE.md`'s domain-doc paragraph still named `Observation`, and its count
was wrong.** Fixed to name `Memory` and to read the count by command
(`grep -c "^## " CONTEXT.md`) rather than retype a number that goes stale
exactly this way; the pre-existing drift in the same sentence (`Workflow` and
`Persona` naming headings that already did not exist) is left alone and
called out rather than fixed, since it predates this ticket.

**`friday/tools/memory.py`'s module docstring still described `Harness`
appending notes to `instructions` in the present tense**, naming a method
this same change deletes. Reworded to past tense with a pointer at what
removed it.

**The claim-and-wire test for the responder's memory tools checked two facts
computed independently rather than the one fact that is supposed to decide
both.** `build_input(has_memory=True/False)` called directly cannot tell "the
flag is right" from "the flag and the wiring happen to agree today" — the
exact failure mode `trust_boundary`'s own guard exists to catch, on the tools
this ticket added instead of the markers ticket 06 added. Rewritten to build
a real `Responder` with and without a store, run `.draft()` through each, and
check the actual per-call prompt (captured via `record=`, the same sink
`collecting()` already uses in this file) against the actual tool list
(`._run.agent.tools`) from the same two constructions.

748 tests pass. Every fix above was deleted once and watched go red,
including the two rewritten tests, which needed a second look to write a
mutation that proved the right thing rather than any red at all.

**`MemoryScope` was living in the wrong module.** It appeared in five
`Database` method signatures as `scope: "MemoryScope"  # type: ignore[name-defined]  # noqa: F821`
— a quoted forward reference because `friday/store/db.py` is not allowed to
import from `friday/tools/`, where the class lived. Every one of those five
ignores meant mypy checked nothing about the one parameter whose entire job is
"never wrong". Moved to `friday/domain/models.py`, beside `Memory` — the
vocabulary both a store and a tool factory are allowed to share — with a real
import replacing all five ignores. `friday/tools/memory.py` now imports it
from there; every test and production import site updated to match.

**`memory_search`'s `limit` had a bare-literal default** (`= 8`), duplicating
`RESULTS` as a number with no test holding the two together — the same
objection `Limits` was retired for, just recurring one field later. The tool
always passes `limit=RESULTS` explicitly, so the default existed only to be a
second copy of the number that could drift from the first. Removed; `limit`
is now a required keyword-only parameter, and a test pins that a caller who
forgets it fails at the call rather than silently agreeing with `RESULTS` by
coincidence.

**The contract-documentation comment in `friday/tools/memory.py` showed the
wrong shape.** `memory_search(scope, query, limit) -> list[Memory]` promised a
positional `limit`; the real signature is keyword-only. Fixed to
`memory_search(scope, query, *, limit) -> list[Memory]`.

755 tests pass, mypy 31 (unchanged). That closes out memory-build-review:
findings 1–6 above, 7 (the move) and 8 (the three items in this paragraph) all
fixed, nothing left outstanding.
