# 02: A model call names the work it belonged to

**What to build:** `model_calls` gains `task_id`, `node` and `latency_ms`, and
the graph's trail is saved beside the checkpoint.

`attempts` was the fourth column and is **deferred to ticket 04** by the
operator's call. There is no retry at the model layer yet, so it would hold 1
on every row — a number that reads like a measurement and is not one. The SDK
retries internally and `_settle` cannot see it; ticket 04 sets `max_retries`

**Blocked by:** 01

**Decisions:** D3

**Status:** done

## Why

`ModelCall` is keyed on `message_id` (`friday/store/schema.py`), which is the
right key for triage — one call, one message — and the wrong key for everything
downstream. An extractor runs on every pass of `prepare_node`, against a task,
reading many messages; a responder draft answers a task, not a message. So
"what did task 42 cost, and which prompts produced this reply" is not a
question the table can answer, and the board's per-message view cannot show
either step.

The graph has the same hole one layer up. `DAGRunner.trail`
(`friday/dag/engine.py:161`) exists only in memory: the checkpoint stores
`results`, and `_checkpointable` strips node 0 out of even that. After a
restart nobody can say which path a run took — including `_outcome`, which
reads the trail to decide what the graph actually decided.

## What it came to

**Three columns and one place that reads a row.** `task_id` is indexed;
`node` says which step of a graph asked; `latency_ms` is measured in
`LogHooks`, per LLM call rather than per run, because a run may make several
and the number worth having is how long the provider took on each. A call cut
off by a timeout carries how long it hung before being cut off, which is the
one number it can still supply. The three readers of `model_calls` each built
the dataclass by hand, so `_model_call` now does it once — a column added to
`schema` used to reach whichever of them somebody remembered.

**The keys travel as `_About`**, a value the harness stamps onto every row a
run produces. Three parameters that travel together and are read together, and
the next one is ticket 04's.

**Threading is the part with the failure mode.** `prepare_node` knows the task
and its own name, and it is the only step that runs an extractor — so that is
where the two meet. `Pool` tells the responder which task it is drafting for.
`tests/test_pool.py::test_the_calls_a_task_causes_are_stamped_with_that_task`
drives the whole chain through `Pool.run_once` with a real `Harness`, because
that chain coming apart in the middle is exactly how the `record=` chain broke
one ticket ago and a unit test at either end would not have noticed.

**The trail is checkpointed with the results**, and a resumed run appends to it
rather than starting empty. One subtlety the first version got wrong: walking
*past* an already-recorded node still counts it, and with a restored path that
counted it twice on every pass — `_resume_point` leaves the loop pointing at
the last recorded node when everything has run.

**The migration had to be made safe, and the first draft was not.** `trail` is
nullable because SQLite cannot add a NOT NULL column to a table that already
has rows, and `dag_state` has them on any deployment that has run a graph. The
first draft failed with "Cannot add a NOT NULL column with default value NULL"
against a database with one row — verified before and after — which per
CLAUDE.md is a boot loop rather than a warning, since `run_agent.py` migrates
before anything opens the database.

**Both routes to a call now exist.** `/api/tasks/{id}/model-calls` answers what
a task cost and what was asked while working on it. `/api/model-calls` answers
the question ticket 01 left open: `uncorrelated=true` narrows to the rows that
name no message, which `model_calls(message_id=None)` never could because that
means "do not filter". The board shows a task's calls folded away under its
card, in one query rather than one per task — the first version rendered two
hundred round trips per page.
