# 02: A model call names the work it belonged to

**What to build:** `model_calls` gains `task_id`, `node`, `latency_ms` and
`attempts`, and the graph's trail is saved beside the checkpoint.

**Blocked by:** 01

**Decisions:** D3

**Status:** todo

## Why

`ModelCall` is keyed on `message_id` (`friday/store/schema.py`), which is the
right key for triage — one call, one message — and the wrong key for everything
downstream. An extractor runs on every pass of `prepare_node`, against a task,
reading many messages; a responder draft answers a task, not a message. So
"what did task 42 cost, and which prompts produced this reply" is not a
question the table can answer, and the board's per-message view cannot show
either step.

The graph has the same hole one layer up. `DAGRunner.trail`
(`friday/dag/engine.py:161`) exists only in memory: the checkpoint stores
`results`, and `_checkpointable` strips node 0 out of even that. After a
restart nobody can say which path a run took — including `_outcome`, which
reads the trail to decide what the graph actually decided.

## Acceptance criteria

- [ ] An Alembic revision adds the four columns, autogenerated against a
      throwaway database
- [ ] `tests/test_migrations.py` stays green — `schema.py` and the migrations
      still describe the same database
- [ ] Every call recorded carries the task it belonged to, where there is one,
      and the node that made it, where there is one
- [ ] `save_dag_state` stores the trail; a resumed run reads it back and
      appends rather than starting an empty one
- [ ] The board and `ops/api.py` can list the calls for one task
- [ ] Each guard is deleted once and watched go red
